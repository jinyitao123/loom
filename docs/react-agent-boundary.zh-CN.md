# Loom ReAct Agent 能力边界

## 目标

Loom 提供可独立复用的单 Agent 执行循环。宿主只注入模型、工具、持久化适配、资源策略和完成验证规则，不再自行实现模型与工具的循环控制、上下文压缩、重复动作反馈或操作回放装饰器。

经典 ReAct 的最小闭环是模型产生下一步行动、环境返回观察、模型依据新观察继续决策。工程产品还需要判断任务是否真实完成，并在失败后继续纠正。因此本文把“完整执行闭环”定义为：

1. 模型根据当前任务和历史选择行动。
2. Loom 执行行动并把真实结果作为观察回填。
3. 重复、工具错误和权限拒绝成为下一轮可见反馈。
4. 模型提出完成时，由宿主提供的只读验证器判断是否满足目标。
5. 验证失败反馈回到同一循环，继续有限纠正。
6. 中断后可从持久状态恢复，已经确认的操作不重复，结果未知的副作用明确停止。

## 归属

Loom 内核继续只包含 `State`、`Step`、`Router`、`Graph` 和 `Store`。通用 Agent 行为位于 `stdlib`：

- `ToolLoop` 负责模型、工具、观察和后续决策。
- `NewToolRepeatGuard` 负责把重复行动转换为模型可见的错误观察。
- `NewSummaryCompactionPolicy` 负责通用上下文摘要和尾部历史保留。
- `NewJournaledLLM` 与 `NewJournaledToolDispatcher` 负责统一模型和工具操作的日志、回放入口。
- 完成验证与纠正循环在后续阶段加入 `ToolLoop`，保持可选、默认行为兼容。

宿主保留以下职责：

- 身份、租约、租户与父任务 fencing。
- 工具清单、权限、凭据与业务副作用策略。
- 业务验收合同、验证器实现与最终用户采用。
- 团队 fanout、成员选择、任务交付和产品界面。

## 第一阶段迁移

第一阶段只归拢已有通用执行能力，不用代码移动伪装成完整 ReAct：

- 将重复行动软反馈从各编译器的私有实现归入 Loom `stdlib`。
- 将 Weave 的默认 LLM 摘要实现归入 Loom `stdlib`。
- 将模型和工具的操作日志装饰、回放解码、活跃执行串行化归入 Loom `stdlib`。
- Weave 的 PostgreSQL 事务、父运行锁、用量累计和产物识别保留为 `ExecutionJournal` 宿主适配。

第一阶段完成后，Loom 仍不能宣称具备完整执行闭环。缺口是模型自然结束仍被直接视为完成，尚无通用完成验证失败后继续纠正的协议；通用操作日志也仍需宿主提供持久化实现。

## 后续验收

完整能力必须由一个不依赖 Weave 的示例证明。该示例只接入模型、工具、Loom Store 和完成验证器，并完成以下过程：工具首次产生不合格结果，验证器拒绝，模型读取拒绝原因后修正，再次验证通过；在模型调用后和带副作用工具调用后分别注入中断，恢复后已确认操作不重复，未知结果不被当成成功。

单元测试、一次正常工具调用或 Weave 业务样本只能证明对应层次，不能代替这项独立验收。
