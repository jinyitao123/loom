# Loom ReAct Agent 能力边界

## 目标

Loom 提供可独立复用的单 Agent 执行循环。宿主只注入模型、工具、持久化适配、资源策略和完成验证规则，不再自行实现模型与工具的循环控制、上下文压缩、重复动作反馈或操作回放装饰器。

经典 ReAct 的最小闭环是模型产生下一步行动、环境返回观察、模型依据新观察继续决策。工程产品还需要判断任务是否真实完成，并在失败后继续纠正。因此本文把“完整执行闭环”定义为：

1. 模型根据当前任务和历史选择行动。
2. Loom 执行行动并把真实结果作为观察回填。
3. 重复、工具错误和权限拒绝成为下一轮可见反馈。
4. 模型提出完成时，由宿主提供的只读验证器判断是否满足目标。
5. 验证失败反馈回到同一循环，继续有限纠正。
6. 中断后可从持久状态恢复，已经确认的操作不重复，结果未知的副作用明确停止。

## 归属

Loom 内核继续只包含 `State`、`Step`、`Router`、`Graph` 和 `Store`。通用 Agent 行为位于 `stdlib`：

- `ToolLoop` 负责模型、工具、观察和后续决策。
- `NewToolRepeatGuard` 负责把重复行动转换为模型可见的错误观察。
- `NewSummaryCompactionPolicy` 负责通用上下文摘要和尾部历史保留。
- `NewJournaledLLM` 与 `NewJournaledToolDispatcher` 负责统一模型和工具操作的日志、回放入口。
- `ErrJournalOutcomeUnknown` 统一标识可能已发生但没有持久回执的操作；工具循环遇到日志执行错误会立即停止。
- `CompletionVerifier` 在模型提出最终结果时执行只读检查；拒绝反馈进入同一 `ToolLoop`，驱动下一轮纠正。

宿主保留以下职责：

- 身份、租约、租户与父任务 fencing。
- 工具清单、权限、凭据与业务副作用策略。
- 业务验收合同、验证器实现与最终用户采用。
- 团队 fanout、成员选择、任务交付和产品界面。

## 第一阶段迁移

第一阶段只归拢已有通用执行能力，不用代码移动伪装成完整 ReAct：

- 将重复行动软反馈从各编译器的私有实现归入 Loom `stdlib`。
- 将 Weave 的默认 LLM 摘要实现归入 Loom `stdlib`。
- 将模型和工具的操作日志装饰、回放解码、活跃执行串行化归入 Loom `stdlib`。
- Weave 的 PostgreSQL 事务、父运行锁、用量累计和产物识别保留为 `ExecutionJournal` 宿主适配。

## 第二阶段补齐

`ToolLoopOpts.CompletionVerifier` 现在提供可选的完成门。模型不再请求工具时，Loom 先提交候选给验证器。通过才生成最终输出；拒绝必须带反馈，反馈作为观察写入历史并继续执行。旧的未配置路径保持原行为。

受控循环还要求稳定的 `CompletionVerifierID` 并把它纳入恢复策略哈希。验证拒绝后的历史会随检查点保存；预算用尽时受控循环暂停，普通循环返回 `ErrCompletionUnverified`，不会把被拒绝候选包装成成功。

这一阶段补上了完成验证与有限纠正机制。通用操作日志仍需宿主提供持久化实现；Loom 规定统一装饰、回放和结果未知协议，Weave 目前负责 PostgreSQL 落盘、事务 fencing 和业务错误映射。

## 库与 CLI

Loom 的主能力以 Go 库提供，`loom run` CLI 调用同一套运行时，服务于跨语言宿主、独立验收和调试。Weave 的主执行路径保持代码引用，因为它需要在同一进程和事务边界内组合父运行锁、检查点与操作日志。若未来引入进程隔离，CLI 可以成为正式适配器，但不能拥有另一套 ToolLoop 或恢复语义。

## 机制验收

`tests/react_agent_test.go` 是不依赖 Weave 的公开接口验收。它只装配模型、工具、Loom Store、操作日志和完成验证器，并在同一场景中验证：模型回执丢失后复用持久结果；带副作用工具回执丢失后不重复写入；不合格结果被验证器拒绝；拒绝反馈跨检查点暂停与恢复后仍可见；模型纠正行动并再次提交后才完成。另一个场景验证结果未知的工具操作会返回 `ErrJournalOutcomeUnknown`，再次执行时不会盲目重放副作用。

这些证据确认 Loom 已具备机制层完整的单 Agent ReAct 执行路径。它们不代表任意模型都能完成任务，也不代表 Weave 已为具体业务配置完成验证器；真实模型、持久化适配器和业务发布物仍需各自验收。
